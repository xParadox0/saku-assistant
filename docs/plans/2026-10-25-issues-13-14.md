# Issues #13 and #14 Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Deliver virtual financial plans/reserves for #13 and complete editable category drill-down filters for #14.

**Architecture:** Extend Saku's existing tenant-scoped `goal` model with an append-only `goal_entry` activity log and weekly/monthly schedule metadata. Serve the plan workspace through authenticated FastAPI/Jinja routes; compute reminders and projections in a pure Python helper. Keep all plan activity separate from `txn`. Complete category detail by adding an accessible GET filter form that preserves the same tenant-scoped spending query and half-open date semantics.

**Tech Stack:** Python 3.11, FastAPI, Jinja2, PostgreSQL/psycopg, pytest, HTML/CSS. No new runtime dependencies.

---

## Decisions and scope

- Plans are virtual-only. They never move or lock money and never create, modify, or delete ledger transactions.
- Contributions and uses are manually entered planning entries, stored separately from `txn`; no automatic linking to ledger transactions in this MVP.
- A use cannot exceed the plan's virtual saved balance. Entries are tenant-scoped and added under a row lock.
- Schedules are optional fixed weekly or monthly amounts. Monthly advancement retains the selected day across short months.
- Reminders are in-app due/upcoming/overdue indicators only; no Telegram/email pushes.
- Projection is `saved balance + scheduled installments from today through target date`; unscheduled or undated plans show an explicit unavailable/ongoing state.
- Existing nonzero `goal.saved` values are migrated once to an `opening` activity entry, preserving the balance.
- #14 already has its core category route in the deployed tree; this work adds explicit controls for category/date changes and clearing, shows category per row, and verifies fee/refund/own-transfer parity.
- No merge, issue closure, public PR, production migration, or deployment is part of this plan.
